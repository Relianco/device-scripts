# Unified Windows Installer P1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the offline-testable contract, discovery/evaluator, planner, rendering, recovery model, and deterministic preview builder for the unified Windows installer.

**Architecture:** Validated data records feed pure policy functions; a narrow read-only probe boundary supplies observations to the same evaluator in runtime and generated detection. A local builder resolves immutable inputs once and emits a digest-bound preview with no deployment entrypoint. Windows execution and durable storage, bundle transport, and Intune delivery follow in P2, P3, and P4 respectively.

**Tech Stack:** PowerShell; plain offline `pwsh` tests without Pester; .NET cryptography and ZIP APIs for the build. Runtime, shared discovery, and generated detector source must use the Windows PowerShell 5.1/.NET Framework 4.8 API and language subset; build/test tooling uses PowerShell 7.4 or newer, but deterministic release assembly supports only the exact writer environment fingerprint fixed and tested in Task 7. Actual 5.1 execution remains a P2 gate, including Unicode/JSON and command-line behavior.

**Spec:** [Reviewed foundation](../specs/2026-11-02-unified-installer-design.md), [recipe specimens](../../design/unified-installer/recipes.md), and [complete scenario matrix](../../design/unified-installer/scenarios.md). Read all three before implementation.

## Global Constraints

- Public documents contain no client names, device IDs, secrets, or home paths.
- Retain PSAppDeployToolkit 4.1.8 as the researched baseline; verify exact API claims.
- Provider APIs stay outside the execution engine. System and User scope are first-class.
- Unknown state is not absence; success requires postcondition verification.
- No runtime imports from live main, ambient modules, or “latest” URLs.
- A hash mismatch exits 1 and is not retried. Reject URL userinfo before any download, including disabled legacy requests.
- Recipes are strict JSON data, interpreted by versioned, reviewed engine primitives. No evaluated expression or executable command string is accepted.
- The initial specimens declare only `ensurePresent`; qualification stays `pending`. Null `minimumOsBuild` blocks release. Initial PSADT pin is `80b45fb8e518ee98774e16e44599d470e4069a0695a6a359022f954edaa83360` for `4.1.8`.
- V1 supports explicit/provider re-entry using a protected resume entry point and operation ID. It does not promise autonomous after-reboot execution.
- Intune publication requires a qualified `ensureAbsent` capability and real uninstall entrypoint; do not generate a dummy/no-op uninstall.
- No device execution, tenant mutation, binary publication, merging, or changes to the legacy runner/packages are authorized by this plan. P1 does not implement mutation, ACL application, atomic disk journals, toolkit sessions, reboot scheduling, or installer launch.
- Tests are offline plain PowerShell scripts discovered recursively beneath `tests/windows` by `tests/run-all.ps1`. Runtime scripts are dot-sourced with `RELIAN_DEPLOY_TEST=1`; no `Mandatory` parameters or import-time effects.
- Workers use isolated `lane/` worktrees, own nonoverlapping paths, and do not edit `docs/STATUS.md` or `docs/plans/`. Commit as `Relian Technologies <112814130+Relianco@users.noreply.github.com>` without a coauthor trailer or AI footer.

## Review Focus

1. Duplicate/case-colliding JSON keys and coercion (`"false"`, arrays instead of integers) must fail before probes; Task 1 tests both raw JSON and record validation.
2. Partially unreadable evidence must retain successful observations and errors without manufacturing absence; Task 2 tests mixed-view failures and malformed versions.
3. A copied operation ID or caller-selected user profile must not change identity/configuration or authorize another SID; Tasks 1 and 6 test binding and reconciliation.
4. Locale, source checkout location, and build timestamps must not alter release bytes; Task 7 tests shuffled object keys, two roots, and cultures.
5. An apparently successful install or detector must not suppress uncertainty or an unresolved operation; Tasks 3, 5, and 8 separately test product truth, operation truth, and generated detector output.

## Shared contracts decided here

Functions accept validated `[hashtable]` records and return `[hashtable]` records, with arrays explicitly retained even for zero/one element. “Typed” means strict recursive validation against closed schemas plus semantic checks, not permissive PowerShell casts. No caller may bypass validation by supplying a hashtable. Before any field lookup, enumerate the original keys, require exact ordinal schema names, and reject decoded duplicates/case collisions. Ordinary caller hashtables with exact keys are accepted then recursively copied into ordinal-comparer records; do not require a particular comparer on input or use case-insensitive lookup to validate spelling. Invalid input throws an ErrorRecord with `FullyQualifiedErrorId=InstallerContract.<Code>`, stable `Code` and field path; the CLI catches it and exits 1. Avoid emitting incidental success-stream objects. Functions never call `exit`; only generated detector/build wrappers do.

**JSON/schema.** Accept at most 1 MiB UTF-8 bytes and nesting 32; reject a UTF-8 BOM, malformed/overlong encoding, unpaired UTF-16 surrogates (raw or escaped), and trailing data. The byte entrypoint decodes with throwing UTF-8 conversion. The 5.1-compatible tokenizer/parser directly materializes strings, integers, booleans, nulls, arrays and ordinal records; never use `ConvertFrom-Json`, `System.Text.Json` or `-AsHashtable`. Date-shaped strings remain strings. Check duplicate and case-colliding names after JSON escape decoding, then exact schema spelling before lookup; unknown fields fail. Numeric fields accept integers only. Canonical output is BOM-less UTF-8: ordinal key ordering, original array order, invariant base-10 integers without leading zeros (zero is `0`), no floats/whitespace/final newline; escape quote/backslash, encode U+0000–U+001F as lowercase `\u00xx`, emit other valid Unicode including `/` as raw UTF-8, and never normalize Unicode. Only `schemaVersion=1`, `requestVersion=1`, `engineCompatibility.major=1` are understood. A new minor vocabulary must be explicitly recognized; reject unknown version representations. Positive recipe revisions; IDs match `[a-z0-9][a-z0-9._-]{0,127}`; lowercase SHA256 is exactly 64 hex characters. OS builds are null or positive integers, timeouts 1–86400 seconds, wait 0–3600 seconds, token arrays at most 128 items of at most 4096 characters, parameters at most 64 names. Reject NUL/CR/LF in executable arguments, paths and identifiers. Versions are strings, not JSON numbers. Closed recipe field names and enum values come from the specimens, with `exact` also recognized for comparison and explicit capabilities for `ensureAbsent`, `repair`, `reinstall`; recognition alone does not supply an implementation or qualification.

**Primitive catalog.** Fixed engine-owned IDs only: discovery `gsaBundleV1`, `sevenZipMsiV1`, `vscodeOwningUserV1`; postconditions `gsaReplacementV1`, `sevenZipInstalledV1`, `vscodeUserInstalledV1`; commands `stagedExe`, `machineMsiInstall`, `validatedGsaCachedBundle`. The catalog maps each ID to code revision/digest, supported scope/actions, required evidence fields and allowed replay points. No naming-based imports, ScriptBlock conversion, dynamic source URLs or executable override. P1 command primitives produce descriptors only. Missing commercial/MSI identity rules, signer evidence, process allowlist or OS qualification are explicit unresolved inputs; preview accepts them as blockers, never invents them. Production registry extension requires reviewed source plus tests and a new source digest.

**Resolved inputs.** `ReleaseInputV1` contains recipe, resolved nonsecret configuration, engine source file inventory, discovery source inventory, PSADT version/hash, brand hash, payload and vendor-cache dependency inventories (`relativePath`, `sha256`, `size`, `role`), qualification evidence references, identity-rule fixtures, trusted profiles, parameter bindings, and `buildFormatVersion=1`. Local absolute paths are builder arguments only, never serialized. Resolver opens local supplied bytes, verifies every hash/size and source binding, and performs no downloads. HTTPS URLs are immutable provenance, not instructions to fetch; reject userinfo, mutable/latest endpoints, unsupported schemes and unresolved `releaseInput` names. Any required signature remains `unverified` until a trusted Windows verification result bound to those bytes exists. External evidence hashes identify evidence; a user-writable JSON claim of `passed` is not release authorization. A caller-provided evidence catalog must itself be trusted by the future release process; P1 only models that check.

**Request and identity.** JSON request is exactly `requestVersion`, `operationId`, `releaseId`, `operation`, `profile`, optional `targetSid`, and `parameters`. `Resolve-InstallerRequest(Request, Release, Invocation)` takes an adapter-owned `Invocation` separately: verified caller SID, SYSTEM flag, elevation, OS/build/architecture, allowed profile IDs, trusted release catalog binding, and trusted parameter policy. Request data cannot supply these claims. Catalog `releaseId` resolves a core digest and bytes, not a mutable URL. `standalone-machine` means SYSTEM/machine/eligible session; `standalone-user` means non-elevated owning user/user/eligible session; `intune-machine` means SYSTEM/machine/Silent; `intune-user` means non-elevated owning user/user/Silent. The standalone-user profile names the native user path implied by the design; it does not impersonate. User target SID must equal the verified caller SID; machine target SID must be absent. Reject elevated administrator as SYSTEM, wrong architecture, unapproved profile or undeclared override before any registry probe. Profiles reduce notification rights; they cannot expand recipe scope. Canonical `requestBindingDigest` binds operation ID, core digest, operation, profile, scope/SID, the release-locked configuration digest, and the canonical effective-parameter digest. Deployment identity for deferral is separately adapter-owned and stable across run IDs.

**Request configuration binding.** Reviewed primitive catalog entries classify each declared parameter as `observable`, `transport`, or `commandOnly`; resolved core `parameterBindings` locks that classification and, for observable parameters, the configuration field path. A caller or adapter policy cannot reclassify a parameter. Resolve defaults and validate types/policy first, then require every observable request value to equal the selected core's resolved configuration value using typed canonical equality. A policy-allowed but differing value fails with `ConfigurationReleaseMismatch` before probes or any effects. Request resolution never patches release configuration or only changes a request digest to accept the mismatch. To change observable configuration, build a new core and detector together and explicitly select that release through the trusted catalog; both `Get-InstallerEvaluation(Release, Observations, ValidationContext)` and generated detection then use that core's configuration. The returned request's configuration is exactly the locked release configuration. Transport parameters may select only preapproved locations for identical pinned bytes (for example `contentSource`); command-only parameters may vary only reviewed execution details proven not to change identity, installed version, scope, observable configuration or postconditions. Both remain bounded and enter the effective-parameter digest; neither enters the detection projection. If an option can affect desired state, classify it as observable and require a rebuilt release. Missing or unreviewed classification is invalid.

**Observation and evaluation.** `ObservationSetV1` contains `releaseCoreDigest`, `discoveryDigest`, `configurationDigest`, `callerSid`, `scope`, OS/architecture, `collectionId`, `collectedAtUtc`, `requestedCoverage`, and probe records. Each probe records kind, explicit hive/view or normalized root, SID, candidate identity, status (`found`, `notFound`, `error`), raw values, and structured error (category, native code, safe message/reference). `ValidationContext` is supplied separately by the trusted adapter/detector boundary, never taken from request parameters or observation claims: expected core/discovery/configuration digests, expected caller SID/scope/OS/architecture, exact required coverage, expected collection ID, `nowUtc` and `maxAgeSeconds=60`. Expected coverage derives from the locked recipe's explicit views, every identity/configuration requirement, coexistence rule and postcondition; missing, extra, duplicate or differently scoped coverage fails closed. Compare all bindings before interpreting values. Future/older-than-60-second evidence, a different collection epoch or caller, or mismatched provenance produces `Unknown` with a specific reason and unsatisfied result. All timestamp fields in records are UTC strings in exact `yyyy-MM-ddTHH:mm:ss.fffffffZ` format; internal invariant DateTimeOffset parsing/comparison is permitted, but DateTime/DateTimeOffset objects never cross record/canonical boundaries. Collection IDs are bounded identifier strings. The evaluator uses only supplied `nowUtc`, never an ambient clock. Collector timestamps and IDs originate at the trusted local boundary; matching self-asserted fields alone are not authority. ValidationContext is a trusted in-memory dependency from that boundary, not authenticated merely because its digest matches the observation. Evaluation records carry the validated bindings, collection ID/time and context digest; planner checks them against `Environment.validationContext`, and reconciliation re-evaluates supplied observations with its trusted validation context. Always collect again immediately before future mutation, even within 60 seconds; no P1 freshness model authorizes real execution.

Preserve raw versions, normalized components, every error and all candidate identities. Empty candidates mean `Absent` only after all required successful not-found probes. Conflicting incompatible identities yield `Ambiguous`; valid registration with a missing required binary yields `Damaged`; unreadable/malformed or untrusted evidence yields `Unknown` and cannot be hidden by a good candidate. Preserve subordinate reasons; blocker order is `Unknown`, `Ambiguous`, `Damaged`, then `Present`/`Absent`. Markers and journals never establish product truth. Independent literal expected-truth and required-coverage fixtures, authored from the recipe/spec rather than collector/evaluator helpers, must assert these rules in addition to parity.

Version primitive is invariant decimal-component comparison: 1–4 nonnegative components, each <= 2147483647, pad missing trailing components with zero; no suffix/prerelease/culture parsing. `26.04` equals `26.04.00.0`. Unsupported vendor forms remain `Unknown` until a reviewed version primitive is added. `EvaluationV1` returns state, all matches, evidence/reasons, version comparison, configuration status (`Satisfied`, `Unsatisfied`, `Unknown`, `NotDeclared`), and boolean `desiredStateSatisfied`. Only supported identity/scope/architecture and declared postconditions can satisfy; arguments are not observable configuration proof.

**Read-only plan.** `PlanV1` contains outcome/reason, binding digest, evaluation, ordered stage descriptors, unresolved requirements, and active-operation reference. Stages are data (`StageContent`, `AcquireLock`, `Recheck`, `Remove`, `Install`, `Verify`), never authority to execute. Active unresolved intent takes priority over `AlreadySatisfied`, while detector remains product-only. Storage, free space, process/session observations and offline closure are supplied snapshots or listed preflight requirements. A dry plan may propose GSA removal/install with `StageContent` unresolved; it cannot fetch content to make that requirement disappear.

**OutcomeV1.** Required fields are `outcome`, `reason`, `phase`, `operationId`, `desiredStateSatisfied`, `mutationStarted`, `rebootRequired`, `retryEligible`, `vendorCode`, `toolkitCode`, `diagnosticReferences`. Raw codes are nullable integers. Satisfied outcomes require proven postconditions; `AlreadySatisfied` also requires no unresolved operation and no mutation in this attempt. `CompleteRebootRequired` requires satisfied postconditions and reboot required. `RebootRequiredIncomplete` requires unsatisfied state and a retained recovery reference in `diagnosticReferences`. `PartialFailure` requires a known completed destructive substep; `NeedsRecovery` includes uncertain effects. Unsafe replay always forces `retryEligible=false`; a newer request may be retryable `Busy` only because it did no work, not because the active operation is replayable. Unknown intent is not cancellation or deferral.

**RecoveryV1.** Closed state fields: `schemaVersion`, `operationId`, `requestBindingDigest`, `releaseCoreDigest`, `configurationDigest`, `discoveryDigest`, `applicationId`, `scope`, `targetSid`, `phase`, `intendedPrimitive`, `attempt`, `bootIdentity`, `precondition`, `expectedPostconditions`, `completionResult`, `lastProcessResult`, `destructiveHistory`, `terminalEvidence`, `ownershipReleased`, `retainedDigests`, `activeReference`, `cancelRequested`, `resumeAction`. The nullable resume action is `Install` or `Verify`; it cannot authorize another removal after reboot. Nullable fields are target SID for machine work, intent/completion before those events, and active reference only before reservation or after explicit terminal reservation release. Digests bind exact input bytes. Attempt is a lifetime nondecreasing count, incremented on every permitted destructive intent. `destructiveHistory` contains monotonic `intentEverRecorded` and append-only `completedSteps` (primitive ID, attempt, verified effect and evidence digest); returning to Ready never resets them. Intent with no completion is uncertainty, not proof of removal. `lastProcessResult` preserves nullable raw vendor/toolkit codes and effect knowledge (`Unknown`, `RemovalVerified`, `InstallationVerified`); `completionResult` is a nullable terminal OutcomeV1, never a bare success flag. `terminalEvidence` is null until completion; `ownershipReleased` starts false and may change once to true. Cancellation can terminate with Complete only when lifetime history proves no intent/effect and completionResult is Cancelled. After known removal, cancellation preserves reservation/content and yields PartialFailure; uncertain destructive intent yields NeedsRecovery. No executable path, argv or script body. Allowed phases: `Planned`, `Staged`, `Ready`, `Removing`, `Installing`, `Verifying`, `AwaitingReboot`, `NeedsReconciliation`, `Complete`, `NeedsRecovery`, `Abandoned`, `Superseded`. Superseded is terminal and does not assert product compliance. A state plus a typed event returns a new record and effect *descriptions*, never writes. An `Intent` event requires verified closure, writable-result proof and identity/lock/recheck proofs; it precedes any future destructive effect. Input proofs are model evidence, not P1 claims about actual ACLs, locks or durability.

### Task 3: Read-only planning and session/process policy

**Files:** Create `Plan.ps1`, `plan.Tests.ps1`; extend fixtures.

**Interfaces:** Consume validated request, evaluation and optional active `RecoveryV1` snapshot validated against the Task 1 shape. Produce `Get-InstallerPlan([hashtable] Release,[hashtable] Request,[hashtable] Evaluation,[hashtable] Environment,[hashtable] ActiveOperation) -> hashtable`. Environment contains supplied session/process/storage/prerequisite/enrollment evidence, validationContext, UTC time and adapter-owned retry/deployment policy. Null active operation is permitted. Reject Complete/Superseded/Abandoned records presented as active. Same operation ID with changed binding is InvalidRequest; matching re-entry reports ReconciliationRequired.
